라플라시안은 필요한가, 학습은 어디에 필요한가

두 개의 질문에 확실히 답한다. ① 라플라시안 행렬이 우리 온톨로지에 필요한가 — 필요 없으면 쓰지 않는다. ② 데이터를 찾기 위한 학습은 정확히 어디에 필요하고, 그 방법론은 무엇인가. 모든 주장은 실제 코드 스캔에 근거한다(추측 아님).

A 라플라시안 행렬 — 필요한가

라플라시안이 주는 것 (딱 세 가지)

L = D − A (차수행렬 − 인접행렬), 정규화형 L_sym = I − D−1/2 A D−1/2. 그래프 분석에서 실제로 쓰이는 성질은 세 가지뿐이다:

  • 0 고유값의 중복도 = 연결 성분(component) 개수 → 그래프 파편화·고아 탐지
  • 두 번째 작은 고유값(Fiedler value) = 대수적 연결도, 그 고유벡터로 스펙트럴 분할·클러스터링
  • e−tL(heat kernel) / 개인화 PageRank = 그래프 위 확산 → 거리에 따라 감쇠하는 다중 홉 이웃 가중치

우리 시스템의 실제 상태 (코드 스캔)

라플라시안이 필요하려면 "지금 하는 일"이 그것을 요구해야 한다. 실제 세 경로를 열어봤다.

grep 결과: laplacian|spectral|eigen|fiedler — 코드베이스 전체 0건. 라플라시안은 현재 어디에도 없다.

유일한 조건부 후보는 ①(확산 기반 검색 확장) 하나뿐이며, 그것마저도 eval 하네스로 폐포 대비 A/B 측정에서 이겨야 채택한다. 측정 없이 라플라시안부터 넣으면 튜닝 못 하는 상수(t 또는 PageRank α)만 늘어난다. 정교함이 아니라 부채다.

B 데이터를 찾기 위한 "학습" — 방법론

가장 흔한 오해를 먼저 깬다. 데이터를 찾는 경로에서 필요한 "학습"의 대부분은 gradient(신경망) 학습이 아니라, 골든셋으로 상수를 정하는 캘리브레이션이다. 검색 파이프라인의 각 단계가 어떤 종류의 "지식"에 의존하는지 분해하면 이게 분명해진다.

검색 경로 4단계 중 gradient 학습이 필요한 단계는 0개. 필요한 건 상수 캘리브레이션(③④)과 사전학습 모델(①)뿐.

방법론 A — 캘리브레이션 (검색이 실제로 필요로 하는 "학습")

상수를 감(感)으로 정하지 않는다. 지어낸 골든셋도 쓰지 않는다. 두 종류의 측정을 엄격히 구분한다 (scripts/eval_search.py의 계약).

1) known-item · 자동

라벨 불필요 — 소여(soundness) 측정

실제 노드의 이름으로 질의해 그 노드가 상위에 오는가. 정답이 "그 노드 자신"으로 자명하므로 라벨이 필요 없다. recall@1/@5 · MRR로 검색이 최소한 자기 이름은 찾는지 검증. 결정론적 표본(정렬 후 균등 간격)이라 재현 가능.

eval_search.py heritage_us --n 100

2) 도메인 관련도 · 수동

골든셋 필요 — 관련도 튜닝

"이 질의에 어떤 노드가 관련 있나"는 사람 라벨이 있어야 한다. 이 골든셋 위에서만 RRF·BM25 가중치·entry_ratio를 실측 튜닝할 수 있다. eval_sweep.py가 설정만 다른 검색기를 나란히 돌려 "어느 knob이 어느 시나리오를 얼마나 움직이나"를 본다.

eval_sweep.py ins_cancer_demo --entry-ratios 0.3,0.5,0.7

지금 이게 왜 문제인가 (정직한 gap)

RRF_K=60·entry_ratio=0.5·BM25×0.1은 코드 주석이 스스로 "측정값이 아니다"라고 적어둔 상수다. 게다가 RRF_K·BM25_WEIGHT는 아직 하드코딩이라 스윕조차 못 한다(eval_sweep.py가 명시). 골든셋도 ins_cancer_demo 한 개뿐. 즉 방법론은 서 있는데 재료(네임스페이스별 골든셋)와 주입 지점(상수 파라미터화)이 비어 있다. 이게 Phase 2의 실체다.

방법론 B — GNN+RL gradient 학습 (검색이 아니다)

진짜 신경망 학습은 ml/에 있다 — 하지만 이건 데이터를 찾는 일이 아니라 "어느 에이전트에 쿼리를 보낼까"라는 라우팅이다. 혼동하면 안 되므로 정확히 구분한다.

왜 B는 "데이터 찾기"의 답이 아닌가

① B는 검색이 아니라 라우팅이다 — 어떤 데이터가 관련 있는지 정하지 않는다. ② torch/PyG 의존이라 커널 경계상 사실의 층에 둘 수 없다(에이전트 스택 소관). ③ 그리고 지금 실제로 작동하지 않는다(GNN+RL 채택 0%). 데이터 검색 품질을 올리려면 B의 학습률을 만지는 게 아니라 A의 골든셋을 채우는 것이 정답이다.

✓ 최종 판정

질문답근거
라플라시안이 필요한가? 아니오 (지금) 코드 0건 · GNN은 spatial이라 불필요 · 성분 세기는 networkx로 충분. 유일 후보(확산 확장)도 측정 전엔 부채
데이터 찾기에 gradient 학습이 필요한가? 아니오 검색 4단계 중 grad 학습 단계 0개. 임베더는 사전학습, 그래프는 결정론
그럼 무슨 "학습"이 필요한가? 캘리브레이션 골든셋으로 RRF·BM25·entry_ratio를 측정해서 정함 = 방법론 A = Phase 2
라플라시안을 언제 재검토하나? Phase 2 이후 eval 하네스가 서면, 확산 확장을 폐포 대비 A/B로 측정. 이기면 그때 채택
한 문장

라플라시안은 지금 필요 없고, 데이터를 찾는 데 필요한 "학습"은 신경망이 아니라 골든셋 기반 캘리브레이션(Phase 2)이다. 정교한 도구를 먼저 들이는 대신, 먼저 측정할 자를 만든다 — 자가 없으면 어떤 정교함도 개선인지 알 수 없다.
