팔란티어는 온톨로지를 어떻게 관리하는가

Foundry / AIP 의 온톨로지 관리 방식을 공식 문서 기준으로 정리하고, 우리 시스템과 대조한다. 결론부터: 객체 모델의 구조는 이미 같다. 벌어진 곳은 변경 통제·측정·생애주기이고, 가장 큰 문제는 우리가 가진 구조를 채우지 못한 채 재고 있었다는 사실이었다.

문서 공식 문서에서 확인 블로그 2차 출처(블로그·강연) 미확인 확인하지 못함

1 온톨로지는 데이터가 아니라 타입 스키마다

네 가지 원시 타입이 전부 스키마로 정의된다 문서: Object Type(실세계 개체의 스키마), Property(특성의 스키마), Link Type(관계의 스키마), 그리고 결정적으로 Action Type — “사용자가 한 번에 할 수 있는 변경 묶음의 스키마”다. 여기에 Function(온톨로지에 결합된 코드 로직)과 Interface(다형성)가 더해지고, 관리 도구는 Ontology Manager다.

“복사가 아닌 의미 계층”은 절반만 맞다. 문서는 온톨로지가 “통합된 디지털 자산 위에 앉아 실세계와 연결한다”고 쓰지만, 동시에 Object Storage V2가 “온톨로지를 뒷받침하는 차세대 정본 저장소”이고 Object Data Funnel이 파이프라인과 사용자 편집을 읽어 색인한다고 명시한다 문서. 즉 “복사 아님”은 거버넌스상의 주장이고, 물리적으로는 전용 인덱스로 물화된다. 우리도 KG 체크포인트 + 벡터 캐시 + 청크 JSONL 로 같은 일을 한다 — 차이가 아니라 동일한 현실이다.
타입 계층이 가운데 있고, 위아래가 모두 그것을 통해 말한다. 쓰기 검증이 Action Type 에 있어 모든 소비자가 같은 규칙을 상속한다.

2 변경 통제 — 온톨로지 수정이 Pull Request 다

온톨로지 브랜치는 “메인에서 파생된 별도 버전”이고, 전역 브랜치 제안을 만들면 온톨로지 제안(Proposal)이 자동 생성된다. 문서가 스스로 “버전 관리 시스템의 Pull Request 와 유사”하다고 쓴다 문서.

  • 리뷰어는 각 작업을 건별 또는 일괄로 승인/거절하고 작업 단위로 코멘트한다.
  • 승인 권한은 리소스 소유권에서 나온다 — 승인자는 기본적으로 해당 리소스의 editor 또는 owner여야 한다.
  • 병합 전 merge check가 실행돼 리소스가 main에 병합 가능한지 검증한다.
  • 가시성이 비대칭이다: 제안의 제목·설명은 온톨로지 접근자면 보이지만, 변경 내용은 해당 리소스 Viewer 이상이어야 보인다.

생애주기 상태는 문서가 아니라 기계가 강제한다

모든 object/property/link/action/interface 에 타입 상태가 붙는다: Promoted · Active · Experimental · Deprecated · Example 문서.

Active

“사용자 애플리케이션에서 실제로 쓰이며 주요 파괴적 변경을 하지 않는다.” active/promoted 리소스는 삭제도, API 이름 변경도 불가하다.

Deprecated

사유 설명 + 삭제 기한을 요구하고, 선택적으로 대체 리소스를 지정한다. “언젠가 정리하자”가 불가능한 구조다.

우리에게 없는 것. 우리는 검수 묘비(tombstone)로 “틀린 개체의 부활”만 막는다. “이 노드는 운영에서 쓰이므로 개명·삭제 금지”라는 계약이 코드에 없다. 실제로 오늘 만든 병합 기능은 노드를 지우는데, 그 노드를 누가 쓰고 있는지 아무도 모른다.

3 계보와 시점 — 어디서 왔고, 그때는 어땠나

Data Lineage는 “데이터가 플랫폼을 어떻게 흐르는지 총체적으로 보는 대화형 도구”이며, 결정적으로 object type 과 dataset 을 같은 그래프에 그린다 — 객체 타입에서 원천 인제스트까지 거슬러 올라갈 수 있다 문서.

시점 되감기는 데이터셋 층에서 지원된다: 데이터셋은 브랜치 위의 트랜잭션으로 버전화되고 (“Git 저장소·브랜치·커밋과 유사”), Time Travel 로 “이전 시점의 데이터를 조회하고, 버전 범위의 변경을 비교하고, 특정 행/값이 언제 바뀌었는지 찾는다” 문서. 다만 객체 단위 as-of 쿼리(“이 직원의 2024-03-01 상태”)는 확인하지 못했다 미확인.

대조. 우리는 더 정밀한 축과 더 빈 축을 동시에 갖는다. 정밀한 쪽 — 청크의 char_start/char_end 불변식으로 문자 오프셋 단위 인용이 되고 (팔란티어는 “원본 PDF 를 나란히 렌더해 대조”한다), 이미지는 (page, bbox)로 주소화된다. 빈 쪽 — 빌드 계보가 없다. 어느 빌드가 이 노드를 만들었고 어떤 LLM·스키마였는지 되짚을 수 없다.

4 품질 측정 — 팔란티어는 골든셋을 제품화했다

AIP Evals는 “LLM 의 비결정적 성질을 다루기 위해 설계된” 평가 환경이다 문서. 구조는 우리 골든셋과 사실상 같다:

AIP Evals우리 (core/search_qa.py)
Test case — 정해진 입력과 기대 출력GoldenCase(query, expected_node_id, accepted)
Evaluation function — 실제 vs 기대 비교 후 케이스별 지표evaluate_cases() → hit@1 · hit@k · MRR · per_case
Target function — 평가 대상(여러 개 가능)channels = {semantic, retrieve, chunk}
버전·모델·반복 간 비교 (분산까지)없음 — 매번 현재 코드만 잰다
Experiments — 파라미터 조합 그리드 서치scripts/eval_sweep.py (부분: entry_ratio만)
우리 스크립트가 스스로 남긴 고백. scripts/eval_sweep.py 헤더에 이렇게 적혀 있다 — “RRF_K·BM25_WEIGHT는 현재 하드코딩 상수라 스윕 대상이 아니다(리팩터 필요).” 게다가 그 스윕은 노드 단위로만 채점하는데, 노드 채점은 구조상 semantic == retrieve로 퇴화한다(retrieve 의 노드 랭킹이 semantic 진입 노드에서 파생). 즉 우리 차별점을 재지 않는 스윕이었다.

5 LLM 결합 — 환각 통제는 프롬프트가 아니라 구조다

LLM 은 도구에 직접 접근하지 못한다. LLM 은 도구 사용을 요청할 수 있을 뿐이고, 그 호출은 호출 사용자의 권한 안에서 AIP Logic 이 실행한다. Palantir Docs — AIP Logic / blocks 문서

세 가지 기제가 명시된다 블로그: ① grounding — 검증된 데이터를 요청하는 도구를 준다, ② 결정적 로직에 위임 — LLM 은 “다음 토큰을 예측”하므로 계산은 함수에 맡긴다, ③ 사람 검토 — AI 가 제안한 Action 을 전문가가 승인/거절한다.

우리 서비스 경계와 같은 형태다. 다만 우리의 “쓰기”는 관리 콘솔의 수동 편집뿐이고, 타입화된 Action·검증 규칙·승인 큐가 없다.

6 비정형 문서 — 우리와 같은 결론에 도달했다

문서 처리 파이프라인이 구체적으로 규정돼 있다 문서: PDF 를 media set 으로 가져오고(media reference 로 참조 — “복사하지 않고 사용”), Pipeline Builder 의 Text Extraction(OCR 포함) → Chunk String(크기·겹침·구분자 설정). 근거로 “임베딩 모델은 최대 입력 길이가 있고, 결정적으로 작은 조각이 검색에서 더 의미적으로 구별된다”를 든다.

그리고 결정적인 한 수: 각 청크가 고유 id 를 가진 온톨로지 객체가 되고, 원본 문서로 링크되며, 임베딩은 vector property 로 저장된다. 인용은 원본 PDF 를 검색 결과 옆에 렌더해 대조한다.

모델은 동형이다. 우리가 더 정밀한 인용 단위를 갖고도 값을 못 낸 이유는 연결 층이 비어 있었기 때문이다.

8 이 대조가 찾아낸 실제 결함

“청크 객체가 문서 객체와 연결되지 않은 상태”는 팔란티어 모델에서 Data Lineage 에 즉시 드러나는 데이터 결함이다. 우리는 같은 모델을 갖고 있으면서 그것을 보는 창이 없었다. 그래서 창을 만들었고, 첫 측정에서 이렇게 나왔다 — ins_cancer_demo 라이브:

골든셋이 깨져 있던 진짜 이유. 정답 라벨은 Disease:유방의 악성 신생물인데 저장된 노드는 Disease:C50( 유방의 악성 신생물 )과 Disease:유방암이었다 — 같은 개념의 세 이름. 라벨이 근거를 못 찾으니 청크 채점은 46건 전부 스킵됐고, 우리는 그것을 “라벨링 UI 가 없어서”라고 오진하고 있었다. UI 를 먼저 만들었다면 깨진 데이터 위에 화면을 얹었을 것이다.

만든 것 — 진단(제시) + 병합(적용), 둘을 분리해서

진단 GET /graphs/{ns}/health

추출 커버리지 · 고아 노드 · 추출 실패 청크 · 중복 군집 · dangling. LLM 0콜, 결정적, 무저장. 개수는 자르지 않고 목록만 표본으로 — 표본을 전부로 오해하면 “다 봤다”가 된다.

병합 POST /graphs/{ns}/nodes/merge

dry_run 기본 True. 옮겨질 엣지, 흡수될 별칭, 재지정될 청크·골든셋 참조, 그리고 사람이 정해야 할 프로퍼티 충돌까지 미리 보여준다.

  • 합치지 않고 제시한다. 자동 병합은 되돌릴 수 없다. 실제로 9군집 중 C73( 갑상선의 악성 신생물 ) ↔ C73(...) 중 중증 갑상선암을 제외한 갑상선암은 다른 개념이다(하나는 제외 집합) — 기계가 판정하면 안 되는 이유의 실물이다.
  • 진 노드의 이름은 별칭으로 흡수한다. 지우면 그 표기로 검색하던 질의를 잃는다. 별칭은 질의 확장이 읽으므로 중복이 동의어로 승격돼 회수율이 오른다.
  • 묘비를 남기지 않는다. 병합은 “틀렸다”(reject)가 아니라 “같은 것이었다”(absorb)다. 묘비를 남기면 그 이름이 재빌드에서 영구 차단되는데, 이제 이긴 노드의 별칭으로 살아 있어야 한다.
  • 정의문을 이어 붙이지 않는다. 두 정의를 합치면 원문에 없는 문장이 생겨 환각이 된다 — 이긴 쪽을 남기고 진 쪽 값은 충돌로 보고해 감사에 남긴다.
  • 청크·골든셋 참조를 함께 옮긴다. 노드만 지우면 청크는 허공을 가리키고 라벨은 조용히 무효가 된다. 골든셋은 추가전용 로그라 재지정도 이벤트로 남긴다(로그가 원본이라는 계약).
병합이 유일한 선택지는 아니다. GoldenCase.accepted 필드는 같은 개념이 여러 노드로 갈린 경우를 정답 집합으로 허용하고, 그 주석이 바로 이 사례를 예로 든다. 채점만 살리려면 accepted 가 가볍고, 그래프 채널의 근거가 쪼개지는 문제까지 고치려면 병합이 맞다 — 판단은 사람 몫이다.
