2검색 스택 — Elasticsearch = 벡터DB + 키워드 검색

온톨로지 검색은 3층 백엔드 위에 그래프-조건부 융합이 얹힌 구조다. ES 가 하이브리드 층을 맡는다.
memory (tier 0)기본 · <2K 노드
numpy 정확 코사인, 무의존
npy (tier 1)자동 · 2K+ 노드
+ 디스크 캐시 — 콜드스타트 8.5s → 0s (실측 6,930배)
⚡ elasticsearchONTOLOGY_VECTOR_BACKEND=elasticsearch
BM25(키워드) + dense_vector(벡터) 하이브리드 — 한 질의 안에서 결합.
조문번호·고유명사처럼 문자 그대로 맞아야 하는 질의는 임베딩만으로 놓친다 → 청크(원문) 검색이 주 사용처.
인덱스 ontology-{ns} · cjk analyzer · int8_hnsw · ES 죽으면 memory 로 degrade (온톨로지가 같이 죽지 않는다)
_score = BM25 × 0.1  +  (cosineSimilarity(질의벡터, 청크벡터) + 1.0)   // aicoach KII 골든셋 실측값 이식 (recall@5 = 0.944)
그 위의 융합 (축 4, /retrieve): 질의 → 진입 노드(의미) → 온톨로지 확장(별칭·is_a 폐포) → 확장 질의 + 노드가 달린 청크, 두 채널을 RRF 로 결합. 온톨로지 · 벡터 · 키워드 세 신호의 결합이 이 시스템의 차별점이다 — 실측: 임베딩 단독이 틀리던 2/4 질의를 교정 (aicoach 는 이 결합이 비어 있었다: 동의어 테이블이 ES 에 닿지 않았다).

유혹판정그 역할의 주인
인증 · 사용자 · 테넌트 관리넣지 않는다logos_api. 온톨로지는 신뢰 경계 안의 내부 서비스로 남는다 (PROTECTED_NAMESPACES 는 사고 방지용이지 권한 체계가 아니다)
대화 · 에이전트 판단 · 오케스트레이션넣지 않는다acp / logosai. 커널 안의 검수 도구 6종은 예외가 아니다 — 자기 데이터에 grounded 되고, 추천까지만 하며, 대화하지 않는다
최종 사용자 UI · 화려한 화면넣지 않는다logos_web. 9275 는 개발·관리 콘솔 지위 유지
물으면 사실을 출처와 함께 돌려주는 것이것만 잘한다— 온톨로지 자신
장기 이전 대상 (역사적 혼합): orchestrator/ 와 ml/ 은 에이전트 라우팅이라 온톨로지의 역할이 아니다. 축 1 이 지연 로딩으로 격리했지만(import 비용 0), 완전한 역할 분리는 acp/logos_api 쪽으로의 이사다 — 호환성을 깨는 작업이라 별도 계획으로.
왜 이 원칙인가 (실측): 온톨로지 프로젝트 3개(Logos/ontology · aicoach · KorAct) 중 Logos/ontology 채택이 0 이었던 이유는 기능이 아니라 역할 혼합의 import 비용이었다 — aicoach 는 KG 엔진 API 를 그대로 베끼면서도 "without pulling its heavy transitive deps" 라는 주석과 함께 재구현을 택했다. 역할 분리는 취향이 아니라 채택의 조건이다.
