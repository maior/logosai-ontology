단계별 상세

P0 · PostgreSQL 토대 완료

core/pg.py — lazy psycopg(없으면 degrade) + 멱등 DDL(ontology.node/edge + 인덱스 7개) + postgres extra. 스키마는 기존 DB 안 ontology, namespace 컬럼 다중화.

검증: 라이브 스키마 생성·왕복, 이웃질의 EXPLAIN = Index Scan using edge_out (O(degree))

P1 · GraphStore seam 완료

core/graph_store.py — 단일 인터페이스 뒤에 InMemoryGraphStore(현재·폴백)와 PostgresGraphStore(인덱스 질의). 서비스의 list_nodes/edges/neighbors 를 seam 에 위임. 백엔드는 ONTOLOGY_GRAPH_BACKEND / ONTOLOGY_PG_NAMESPACES 로 선택.

검증: memory ↔ PostgreSQL 반환 payload 바이트 동일 (계약 테스트) · admin 60 무회귀

P2 · dual-write & 라이브 전환 완료

sync_from_graph (KG→PG 멱등 미러) + 빌드/인제스트 hook + migrate_namespace_to_pg (+POST /graphs/{ns}/migrate-pg). PG 는 진짜 인덱스 COUNT 라 근사 COUNT_CAP 밴드에이드 제거.

검증: demo_ko 를 PG 로 전환 — PG-only sentinel 삽입 시 HTTP 9→10 로 PG 서빙 증명, 제거 시 복귀

P3 · Elasticsearch 검색·파셋 완료

core/object_index.py — 객체 인덱스 ontology-obj-{ns}, BM25(name 가중) + type/trust keyword 파셋(aggregation). object_search() + GET /graphs/{ns}/object-search (ES 없으면 PG substring 폴백, source 필드로 구분).

검증: q=경주 → Region:경주 관련도 최상위, type/trust 파셋 · demo_en(memory) → fallback

P4-a · 검색 UI 배선 + 콜레이션 정합 완료

관리 콘솔 검색창을 object-search 에 연결 — ES BM25 관련도 정렬 + 타입/신뢰 파셋 칩(클릭 좁히기, 결과로 재계산). PostgresGraphStore 정렬을 COLLATE "C" 로 memory 와 순서까지 일치.

검증: demo_ko “경주” → 관련도 랭킹·파셋·좁히기 라이브 · 순서-민감 parity 테스트

P4-c · 검색 품질 측정 하네스 완료

scripts/eval_search.py — known-item(자동, recall@1/@5·MRR) + 사람 라벨 골든셋(--golden). 골든셋을 지어내지 않고 소여와 관련도 튜닝을 구분.

베이스라인(200질의): heritage_us recall@5 1.000·MRR 0.990, heritage_kr 1.000·0.998

P4-b(1) · 수동 변경 PG 이중기록 완료

생성·편집·거절·엣지·타입개명이 KG 만 바꾸고 PG(읽기 진실)엔 반영 안 되던 문제 해결. PostgresGraphStore 쓰기 프리미티브 5종 + _pg_apply(PG-backed·접속가능 시 이중기록, 실패는 ERROR). stats/개요/node_detail 도 seam 으로 이관해 개요 조회가 전체 그래프 로드 없이 PG 인덱스 GROUP BY.

검증: 라이브 이중기록 E2E(demo_ko 생성→PG·엣지→PG·거절→PG 0/0, 정리)

P4-b(2) · 증분 미러 완료

sync_from_graph 가 content_hash diff 로 변경/신규만 upsert·사라진 것만 delete — 미변경 행은 쓰기 0. 대용량에서 매 빌드 전체 재기록(이전 delete-all+insert-all)을 없앤다.

검증: 미변경 재동기화 시 updated_at 불변(재기록 0) · 라이브 heritage_us 2차 “노드 ~0/-0”

구조화 검색 + 코호트 추출 완료

프로퍼티 값(=·포함·있음) + 노드 관계(술어·대상·대상타입·방향)로 찾기(/query, PG jsonb+EXISTS) + 탐색 “고급 검색” UI. 검색 코호트를 그대로 RL/LLM 학습데이터로 추출(triples/qa/surface/evidence, /dataset + c_* 다운로드).

라이브: 관계 “→State” 1,985 · museum 코호트 42노드→254행 추출

P4-b(3) · 빌더 PG 직접기록 의도적 비목표

빌더가 개체별로 PG 에 직접 쓰는 것은 안티패턴 — 인제스트 중 수천 왕복이라 증분 미러(배치)보다 느리고 위험하다. (1)+(2)로 PG 는 이미 커밋된 진실이고 일관적이라, 이 단계는 하지 않는다. 인제스트는 KG(작업 버퍼)→증분 미러(PG 진실) 방향을 유지.

실측 근거 (제안서 인용용)

대용량 라이브 전환 — heritage_us 3,623 노드 / 6,852 엣지, heritage_kr 2,784 / 5,707 을 PG 진실 원본으로 전환. 브라우즈 total=3,623 · capped=false(근사 아닌 진짜 인덱스 카운트), HTTP 255 ms.

인덱스 이웃질의 — 최고차수 허브(degree 1,963)의 이웃 조회 318 ms, 일반 노드는 그 이하. 전체 그래프 스캔 없이 O(degree).

검색·파셋 — heritage_us “museum” 55 hits 57 ms(엔진) / 332 ms(HTTP), 타입 파셋 {museum:17·HeritageClass:15·house:8}.

검색 품질 — known-item 200 질의 recall@5 = 1.000(전 질의 상위5 내), recall@1 ≈ 0.98–0.995.

정직한 한계

정렬 콜레이션 — 해결(P4-a) · PG 정렬을 COLLATE "C"(바이트=코드포인트)로 memory 와 순서까지 일치. 순서-민감 parity 테스트로 고정.

증분 미러 — 해결(P4-b2) · content_hash diff 로 변경분만 반영, 미변경 쓰기 0. 전체 재기록 제거.

도메인 관련도 튜닝 — known-item 소여는 recall@5=1.000 으로 측정됐으나, RRF·검색 가중치의 관련도 튜닝은 사람이 라벨한 골든셋이 있어야 한다(하네스 준비됨, --golden).

빌더 진실 방향 — 읽기·개요·수동변경은 PG(진실)에 직행·이중기록되나, 인제스트는 여전히 KG(작업 버퍼)→증분 미러→PG 방향이다. 빌더 개체별 PG 직접기록은 배치 미러보다 느리고 위험해 의도적 비목표(P4-b3). 실용상 PG 는 커밋된 진실 역할을 한다.
