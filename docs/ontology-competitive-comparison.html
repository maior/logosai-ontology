Ontology · 제안서 참고자료 (정부과제)

왜 이 온톨로지인가 — 경쟁 시스템과의 비교

RDF/OWL 트리플스토어, 순수 벡터 RAG, LLM 지식그래프 빌더, 상용 플랫폼(Palantir), 그래프DB 와 나란히 놓고 본다. 경쟁자의 진짜 강점은 인정하되, 정부·공공이 실제로 요구하는 축 (검증 가능성·출처 추적·온프레미스 주권·감사·한국어)에서 우리의 우위를 정직하게 정리한다.

⚠️ 제안서 인용 원칙 — 이 문서는 구현·검증된 것과 설계·로드맵을 구분한다. “✓ 강함”은 이 저장소에서 라이브로 검증된 기능(711 테스트, demo_ko 라이브 전환)에 한한다. 과장은 정부 제안서의 신뢰를 깎는다 — 표의 △/✗ 를 숨기지 말 것.

1 경쟁 지형 (한눈에)

그림 — 우측 상단(검증가능 + 자동 구축)은 상용 독점(Palantir)만 점유하던 지대다. 본 온톨로지는 그 지대를 개방·온프레미스·한국어로 채운다.

3 경쟁 우위 — 정부·공공이 요구하는 축

1. “그럴듯한 답”이 아니라 “인용 가능한 답”
모든 사실이 신뢰 등급 + 원문 문자 오프셋까지 추적된다. 감사·규제 대응이 필수인 공공에서, 순수 벡터 RAG 의 환각 위험을 구조적으로 차단한다 — 답에 출처와 신뢰도가 함께 나온다.
2. 데이터 주권 · 온프레미스 · 해외 SaaS 불요
전 구성요소가 자체호스팅 가능(PostgreSQL·Elasticsearch·자체 임베더). Palantir 같은 독점·해외 플랫폼 의존 없이, 국내 폐쇄망·기관 내부망에 그대로 올린다. 벤더 lock-in 없음.
3. 문자 그대로 맞아야 하는 질의 (조문번호·고유명사)
법령 조문번호, 기관명, 고시 번호처럼 문자 그대로 맞아야 하는 질의를 임베딩만으로는 놓친다. BM25(키워드) + 벡터(의미) + 그래프(별칭·상하위) 세 신호를 RRF 로 융합해 잡는다.
4. 감사·검수 루프가 내장
LLM 추출분을 인간이 confirm/reject 하고, 삭제는 묘비(tombstone)+이력으로 남는다. “누가 왜 이 사실을 승인/기각했나”가 감사 가능 — 공공 데이터 거버넌스 요건에 부합.
5. 무겁지 않게 채택 (degrade 설계)
무거운 구성요소(임베더·ES·PG·torch)는 전부 선택적이고, 없으면 죽지 않고 품질만 내려간다. 소규모 기관은 가볍게, 대규모는 인덱스 서빙으로 — 같은 코드가 규모에 맞춰 확장.
6. 한국어 우선
한국어 임베더(ko-sroberta), 한글 정확 검색, 한국어 도메인 골든셋 기반 튜닝. 영어권 도구를 이식한 것이 아니라 한국어 문서를 1차 대상으로 설계.

4 정부과제 정합성

데이터 주권 · 정보보안

폐쇄망 온프레미스 배포, 해외 클라우드 의존 제거, 벤더 lock-in 없음.

설명가능성 · 감사

모든 사실에 출처·신뢰등급, 판정 이력·묘비로 의사결정 추적 가능.

국산·개방 기술

오픈 구성요소 기반 자체 개발, 한국어 최적화, 소스 통제권 보유.

단계적 도입

degrade 설계로 소규모 PoC→대규모 확장까지 동일 코드베이스.

5 제안서 삽입용 문단 (그대로 붙여쓰기)

본 사업의 지식 표현 계층은 검증 가능성과 자동 구축을 동시에 달성하는 온톨로지 엔진을 채택한다. 문서로부터 LLM 이 개체·관계를 자동 추출하되, 모든 사실은 신뢰 등급과 원문 출처(문자 단위)까지 추적되어 설명가능성과 감사 요건을 충족한다. 검색은 키워드(BM25)·의미(벡터)·온톨로지 그래프의 세 신호를 융합하여, 법령 조문번호·고유명사처럼 문자 그대로 일치해야 하는 질의와 의미 유사 질의를 함께 처리한다. 저장 계층은 PostgreSQL 을 진실 원본, Elasticsearch 를 검색 투영으로 분리한 구조로 대용량 인덱스 서빙을 제공하며, 모든 구성요소가 온프레미스 자체호스팅 가능해 데이터 주권과 정보보안 요건을 만족한다. 상용 독점 플랫폼과 달리 벤더 lock-in 이 없고, 한국어를 1차 대상으로 최적화되어 있다.

※ “대용량 인덱스 서빙”의 현재 실측 근거: 단일 네임스페이스 3,623 노드 PG 전환, 진짜 인덱스 카운트(근사 아님)·이웃질의 O(degree)·검색 recall@5=1.000. 목표 규모(수천만)는 인덱스 구조상 확장 가능함을 뜻하며, 과제 규모에 맞춰 실측치와 함께 명시할 것.

6 정직한 한계 (제안서 신뢰를 위해)

형식 추론 — 완전한 OWL/DL reasoner 는 목표가 아니다. is_a 폐포·그래프 확장 수준의 실용 추론에 집중한다. 엄격한 논리 추론이 핵심 요구면 RDF/OWL 스택과의 결합을 검토.

검증 규모 — 인덱스 구조로 수천만까지 설계. 라이브 검증은 현재 단일 네임스페이스 3,623 노드/6,852 엣지(heritage_us) PG 전환 + 진짜 인덱스 카운트·이웃질의(허브 deg 1,963, 318 ms) 단계다. 대규모 서빙 최적화(수동변경 이중기록·증분 미러—미변경 쓰기 0)는 완료. 실제 수천만 부하 실측은 데이터가 그 규모에 이를 때.

관련도 튜닝 — known-item 검색 소여는 recall@5 = 1.000(200 질의)으로 측정됐으나, RRF·검색 가중치의 도메인 관련도 튜닝은 사람이 라벨한 골든셋이 필요하다(측정 하네스는 준비됨). 과제 데이터에 맞춘 튜닝을 전제로 한다.
