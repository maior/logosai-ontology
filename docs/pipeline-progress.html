업로드 한 번 → 검색 가능한 사실

"문서를 올리면 검증 가능하고 에이전트가 소비 가능한 지식베이스가 된다"를 실물로 만드는 작업. 네임스페이스 생성 → 업로드 → 자동으로 지식그래프·벡터DB·원문 청크·검색 인덱스가 채워지고 → /retrieve 로 근거와 함께 답한다. 인제스트 품질(Phase 1)과 검색 품질 측정 기반(Phase 2)이 완료됐고, 측정이 이끈 정직한 결론들 — 되돌린 설계 포함 — 을 함께 기록한다.

북극성 — 하나의 업로드로 채워지는 네 개의 층

사용자는 문서 하나를 올릴 뿐이다. 그 뒤로 네 가지가 자동으로 채워지고, 그 위에서 그래프-조건부 검색이 근거를 붙여 답한다. aicoach 가 "약관→벡터DB→(별도)KG" 였다면, 여기서는 업로드가 곧 전 층 적재다.

② 업로드는 ③ 네 층을 자동으로 채운다 — 신규 네임스페이스도 예외 없이. ④ /retrieve 가 세 신호(온톨로지·벡터·키워드)를 융합해 근거와 함께 답하고, ⑤ 브리지 에이전트가 grounded 도구로 소비한다.

Phase 1 — 인제스트 품질: 쓰레기 넣으면 쓰레기 나온다

검색·추출·인용의 상한은 청크 품질이 정한다. 약관 PDF 의 반복 노이즈와 무구조 분할을 먼저 잡았다.

구조-인지 조문 세그먼터 완료

약관·법령을 조(제N조) 단위로 정확히 분할하고 인용 라벨을 청크에 싣는다. 본문 속 외부 조문 참조("제1조의…", "제1항")는 조사 부착·인용부호로 판별해 경계로 오인하지 않고, 목차는 점 leader 밀도로 폐기하되 텍스트는 변형하지 않아 오프셋 불변식을 유지한다. aicoach legal.py 이식

실측: 제1조【목적】…제2조【용어의 정의】… 91개 조-단위 청크(92조 중), 대부분 정순, 오프셋 불변식 True

PDF 리더 정규화 완료

반복 러닝헤더(숫자 정규화 후 빈도 ≥40%·≤60자), 쪽번호 줄("12 / 313"), 우측정렬 꼬리말 접두를 제거한다. 정규화본을 그대로 "원본"으로 저장해 청크·오프셋·인용이 한 기준으로 일관. 한글 PDF 자간(단어 내 공백)은 건드리지 않는다 — 잘못 붙이면 의미가 훼손되고, cjk 검색은 자간이 있어도 동작한다.

실측(본문 20p): 러닝헤더 완전 제거, 꼬리말 20→1, 조 라벨 91개, 오프셋 불변식 True

소스별 멱등 재적재 완료

같은 문서를 다시 올리면(내용이 바뀌면 새 해시 id) 옛 청크가 쌓이던 문제를 해결. 청크는 source 와 1:1 이라 재처리 전에 그 소스 청크를 비우고 다시 넣어 "교체" 의미를 준다 — 첫 적재면 no-op, 다른 문서엔 무영향. 노드는 type:name upsert 로 이미 멱등.

테스트: 소스 격리·역인덱스 정리·교체 3종 + 빌더 재적재 교체 1종

인용 칩 (제N조 라벨) 완료

세그먼터가 chunk.section 에 실은 조 라벨을 인스펙터 '근거 청크' 패널에 인용 칩으로 노출. 인용이 "약관.pdf · [1234-1890]" 이 아니라 "제19조(청약의 철회)" 를 가리킨다 — 사람이 검증 가능한 출처.

근거 추적: 노드 → 청크 → 원문 문자 오프셋 → 조 라벨 사슬 완성

업로드 자동화 — 게이트 뒤에 막혀 있던 검색 인덱스를 트다

진짜 원인은 _mirror_to_pg 의 ES 투영이 pg_backed 게이트 뒤에 있어 신규 네임스페이스는 검색·벡터 인덱스를 못 받던 것. 게이트와 무관하게 채우도록 풀었다.

업로드 시 자동 색인 + 회수 추출 + 미리보기 + 관리 화면 완료

A · 자동 인덱싱 — index_namespace() 가 ES 노드 인덱스와 청크 벡터 인덱스를 PG 게이트와 무관하게 채운다(best-effort — 인덱싱 실패가 빌드를 깨지 않음). 빌드 끝에 "indexing" 진행 단계 연결.

B · 토픽 회수 추출(aicoach식 옵션) — extraction_mode=topic: 전 청크를 저장·임베딩(벡터DB 완전)한 뒤 토픽별 상위 청크만 LLM 추출 → 대용량 약관을 저비용·집중 처리. 토픽은 LLM 자동 도출(도메인 하드코딩 없음), 회수 0 시 전체 폴백.

C · 벡터화 전 미리보기(교감) — 수집은 준-비가역·유상 작업인데 사용자가 '무엇으로 벡터화되는지' 모른 채 버튼을 눌렀다. 감식 응답에 ingest_config 를 실어 확인 단계에서 임베딩 모델·청크 크기·ES 인덱스명을 미리 보여준다.

D · 검색 인덱스 관리 화면 — GET /index-status(ES 문서수·동기·벡터 가용성), POST /reindex(과거 데이터·편집 후 drift 복구).

실측: ins_cancer_demo 업로드→감식 시 미리보기 카드에 ko-sroberta-nli · 800/120 · ES 하이브리드 · ontology-obj-ins_cancer_demo 표시

Phase 2 — 검색 품질을 감이 아니라 숫자로

"어느 knob 을 어느 방향으로" 가 나오도록, 질의를 시나리오 축으로 태깅하고 /retrieve 를 1급 측정 채널로 승격했다.

골든셋 2축 태그 시나리오

질의를 매칭 성격(exact · semantic · graph)과 의도(coverage · definition · procedure …)로 태깅해 채널×태그로 분해. 생성기(QAGenerator)는 이름 금지 패러프레이즈만 만드므로 초안은 semantic 태그를 기본 부여, exact/graph 는 손 시드 몫으로 남긴다. n=8 → 38 로 확장(손 8 + 생성 30, 생성분은 draft — 정식 확정은 사람).

/retrieve 를 1급 측정 채널로 어댑터

청크 반환 /retrieve 를 노드 단위 골든셋으로 재려면 어댑터가 필요하다. retrieve_result_to_nodes(순수 함수)가 결과 전체를 노드 랭킹으로 매긴다 — 우선순위 entry_nodes(질의 직접 매칭) → expanded_nodes(그래프 hop) → 청크 hit node_ids, 첫 등장 유지 dedup.

측정이 이끈 개선 (Phase 2-A): 초기엔 /retrieve 를 청크 hit 의 node_ids 평탄화로만 랭킹해 정답 노드가 뒤로 밀려 hit@1 이 구조적으로 0 이었다("맞는 조항은 찾지만 노드 랭킹이 약하다"). entry-node 우선 재정렬로 hit@1 0.00→0.50, hit@5 0.62→0.88, mrr 0.22→0.61 — 태그별 definition/exact/procedure 는 0.33~0.50 → 1.00. 이로써 retrieve = semantic 진입 + 그래프/청크 보강 이라 semantic 이상이 구조적으로 보장된다.

측정이 남긴 네 개의 정직한 결론

  • 유지(a) retrieve = semantic entry + 보강. 진입 노드는 의미 매칭으로 잡고, 그래프 확장·청크 hit 로 보강한다. 이 구조 덕에 retrieve 는 semantic 채널 이상을 구조적으로 보장한다.
  • 기각(b) entry_ratio 는 레버가 아니다 — 스윕이 증명. 골든셋으로 er=0.3 · 0.5 · 0.7 를 나란히 재니 지표가 전부 동일(hit@1=0.38, hit@5=0.88, mrr=0.56). 정답 노드가 대개 최상위 entry 라 저득점 entry floor 변경이 top-k 를 안 바꾼다. 스윕 하네스가 이 낭비를 미리 막았다.
  • 진단(c) coverage/semantic 갭은 임베딩 리콜 문제 — 랭킹이 아니다. 실패 질의의 정답 노드가 어느 채널에서도 상위에 없다. 다음 레버는 임베더·질의확장(리콜)이지 노드 랭킹 재배열이 아니다.
  • 되돌림(d) 2-D RRF 3-소스 블렌드 → 측정이 기각 → 되돌림. coverage 회복을 노리고 노드 랭킹을 RRF 융합으로 바꿔봤으나 더 나빴다(retrieve hit@5 0.88→0.75, definition/exact/procedure 후퇴, coverage 0.60 그대로). (c) 때문에 RRF 로는 못 고친다. 코드는 되돌리되 docstring 에 실험 결과를 남겨 같은 재시도를 막는다.

별칭에 통용 통칭 허용 가1

coverage/semantic 미스의 한 축은 "유방암"(질의)↔"유방의 악성 신생물"(문서)처럼 문서엔 정식명만 있어 임베딩·BM25 가 못 잇는 것. definition·사실은 여전히 텍스트 근거 필수(반환각 금지 불변), aliases 만 널리 통용되는 통칭·약칭을 허용 — "확실히 같은 대상일 때만" 가드.

핵심 원칙 — 이 작업을 관통하는 세 가지

① 측정 기반 개발. 허영 개선을 강행하지 않는다. 측정이 기각한 설계(RRF 블렌드)는 되돌리고, 레버가 아닌 knob(entry_ratio)은 스윕으로 미리 걸러 낭비를 막는다. "되돌린 실험"은 약점이 아니라 측정이 작동한다는 증거다.

② 하드코딩 어휘 금지. 별칭·확장어는 코드 리터럴이 아니라 그래프에서 읽는다. 토픽도 LLM 자동 도출이라 도메인 하드코딩이 없다. aicoach 의 _SYN 동의어 테이블이 하려던 일을 데이터로 한다.

③ 서비스 경계. 온톨로지 = 사실의 층(지식 표현·grounded 검색·데이터셋), 판단 = acp, 오케스트레이션 = logos_api. 인제스트·검색 파이프라인은 전부 사실의 층 안에 머문다.

aicoach 대비 — 무엇이 다른가. aicoach 는 "약관→벡터DB→(별도)KG" 였고 동의어 테이블이 ES 에 닿지 않아 하드코딩 리터럴로 편향을 막아야 했다. 여기서는 (1) 더 일반적 — 도메인 하드코딩 없이 스키마·별칭·토픽을 데이터로 다루고, (2) 업로드 통합 — 한 번의 업로드가 KG·벡터·청크·검색 인덱스 네 층을 동시에 채우며, (3) 재현 가능 — 스키마 고정으로 재인제스트가 node_id 를 깨지 않아 골든셋이 계속 유효하다.
