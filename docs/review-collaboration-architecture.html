1. 왜 — 세 병목의 실측

① 사람 검수 처리량

PROJ-A node_review 1,596 · 재라벨 33 · 중복 45. 후보 생성은 싸졌는데 판정은 전부 사람 — 확률적 제안 시스템의 구조적 병목. 검수 에이전트 6종이 커널에 있으나 recommend 배선은 1종(근거대조)뿐이고 조율기가 없다.

② 기각의 무기록 (관계)

관계 백필 기각 10건 중 8건이 이전 라운드에서 이미 기각된 패턴의 재출현 (전이 3 · 시점 2 · 조건절 sameAs 2). 원인: 승인만 relation_approve 로 남고 기각은 응답 JSON 으로만 반환되어 디스크에 없다. 재출현 제외 시 신규 제안 정답률 87%.

③ 커버리지의 사후 발견

추출 커버리지 12%(PROJ-A 요구서 초기)가 몇 주간 아무 경고 없이 방치됐다. check_coverage 호출 지점은 수동 API 1곳뿐 — 빌드 완료 시 지표 비교·경고가 전혀 없다.

3. Ⓐ 기각 관계 registry — 관계판 묘비

노드 묘비는 무조건 거른다. 관계는 주장이라 다르게 간다 — 혼합 스코프:

상황처리근거
기각 트리플이 같은 청크에서 재제안거른다 (rejected_filtered 로 셈 보고) 같은 원문·같은 주장 — 재출현 정보가 0. 실측 8/10 이 이 부류
기각 트리플이 다른 청크에서 재제안표시 (previously_rejected 동봉) 후 사람에게 지난 기각은 "그 인용이 지지하지 않는다"였을 수 있다
검수자가 scope:"triple" 기각 (기본값)어느 청크에서 와도 거른다 실측 기각 사유 전부가 주장 자체의 왜곡 (전이→보장 등)
{"action": "relation_reject", "node_id": "<subject>", "reason": "전이를 보장으로 왜곡",
 "after": {"predicate": "coversDisease", "target": "<object>",
           "chunk_id": "…", "evidence_quote": "…", "scope": "triple"}}
  • 파생 상태 _rejected_relations[(s,p,o)] — 키 정규화는 _squash_ws 재사용 ('같다' 정의 한 벌)
  • 나중 판정이 이긴다: relation_approve 가 같은 트리플 묘비를 걷는다 (replay 순서 = 시간)
  • approve 는 기각 트리플 기본 skip + 명시적 override_rejected 만 통과 (조용한 번복 차단)
  • API: POST /review/relations/reject (reason 필수) + 보드에 관계 패널 신설 (현재 관계 UI 는 0)

4. Ⓑ 커버리지 expectation 게이트 — 팔란티어 차용

4대 결정
  • 자는 새로 안 만든다 — graph_health.health_report 의 기존 지표 + 임계 비교만 (게이트와 health 탭이 같은 자)
  • 기본 임계 없음 — 미설정이면 unconfigured 로 지표만 보고 (ins 100% vs PROJ-A 25% — 네임스페이스마다 정답이 다름은 실측)
  • 경고 게이트 — 빌드는 항상 완료, coverage_gate.warnings 만 리포트·콘솔에 (expectation 의 본뜻)
  • 0/0 정직 — 청크 0 이면 경고 대신 measured:false ("측정 안 됨" ≠ "미달")
  • core/coverage_expectations.py — retrieval_config 골격 복제 (_SPEC 검증 · 부분 오버라이드 · None=삭제 · 네임스페이스별 파일 · 감사)
  • 배선 지점은 잡 러너 2곳 (_run_build_job / _run_ingest_job) — BuildReport 데이터클래스는 무변경
  • GET /coverage-gate (현재 상태 재평가, 0콜) + GET/POST /coverage-expectations
  • 임계 미달 시 check_coverage 자동 실행은 옵트인·기본 off + 콜 예산 상한 (비용을 측정 없이 물리지 않는다)

밴드 규칙 (결정적)

  • strong_confirm LLM confirm ∧ 인용 실재 ∧ 근거 ≥1 ∧ 중복 비소속 ∧ 일관성 0 ∧ 구조단위 아님
  • strong_reject LLM reject ∧ 사유 있음 ∧ 인용 실재 — 결정적 신호만으로는 만들지 않는다 (근거 0 = relink 실패일 수 있음)
  • borderline 그 외 전부 → 사람. 관계는 2분류로 시작 (기계 기각 없음 — 시그니처 위반 다수가 정상이라는 실측 유지)
일괄 승인의 안전핀 — 자 없이 자동화 없음

일치율 자(recommendation_agreement — recommend ↔ 이후 사람 판정, 로그 replay 에서 공짜 파생)가 렌즈별로 붙고, 표본 n<20 이면 일괄 버튼이 비활성된다. judge-batch 는 본문 불신(최신 추천 재대조, 낡은 추천 skip) + dry-run 미리보기 = 적용 계약. RL 채택률 0% 진단의 "하지 말 것"(측정 없는 자동화)과 같은 규율이다.

6. Phase 순서와 병렬 트랙

A1 review_store 관계 묘비 + replay·변이 테스트 (+ clear 누락 버그 동시 수리)
A2 propose 필터/표시 + approve skip/override + reject API
A3 보드 관계 패널 (제안·승인·기각 UI 신설)
C1 결합기 + triage API + recommend 기록 (A2 이후 — previously_rejected 신호 필요)
C2 일치율 자 + quality API
C3 밴드 UI + judge-batch 일괄 승인 (C2 이후 고정 — 자 먼저)
B1 expectations config + evaluate 순수 함수 (A 와 병렬)
B2 잡 러너 배선 + /coverage-gate + 콘솔 경고
B3 auto_check 옵트인 (측정 후 기본값 재론)

A2 까지만 배포돼도 다음 백필 라운드부터 8/10 재출현이 사라진다 — 가장 싼 최대 효과. A 트랙과 B 트랙은 파일 겹침이 거의 없어 병렬 구현 가능, C 는 A2 를 기다린다.

8. 위험과 완화

위험완화
자동화 안주 — 일괄 승인이 사실상 자동 판정화일치율 자 + n<20 비활성 + 배치 상한 + dry-run 강제 + recommend 전량 감사
관계 묘비 과도 차단 (정당한 재제안까지)rejected_filtered 노출 + 묘비 목록 API + override 경로
경고 피로 (warn 상시화)기본 unconfigured — 임계는 운영자가 명시적으로 건다
LLM 비용 폭주결정적 렌즈 선행 콜 절감 + limit 예산 + 온디맨드 실행 + auto_check 옵트인
트리플 키 정규화가 인용 검증과 갈라짐_squash_ws 단일 재사용 + 변이 테스트 (방향·쌍-키·정규화 mutant 사살)
