1. 왜 — 인벤토리가 확정한 세 gap

① 비용을 재는 자가 0개

자 4종(골든셋·슬롯·라우팅 홀드아웃·커버리지) 전부 품질만 잰다. "온톨로지 검색이 hit@1 2.8배"는 알지만 그 대가(지연 ms·임베딩 콜·확장 노드 수)는 어떤 자에도 없다 — 효율은 품질/비용인데 분모가 없다.

② 실험이 재현 불가

3단 비교(벡터/온톨로지/에이전트)·임베더 비교·knob 스윕 — 전부 CLAUDE.md 표와 코드 주석으로만 남았다. 유일한 스윕 스크립트는 entry_ratio 1축·target=node 고정·이력 미기록.

③ 조합 간 비교 화면 없음

타임라인은 시간축 하나. "설정 A vs B 를 나란히"를 보는 화면·API 가 없어 결론이 사람 기억에 산다 — 그리고 이 세션에서 그 결론이 두 번 뒤집혔다.

3. 효율의 정의

축지표출처
품질hit@1 / hit@k / MRR (target=evidence 기본) + by_tag기존 evaluate_cases — 신규 지표 코드 0줄
비용질의 지연 p50 / p95 (워밍업 1질의 제외 — 콜드스타트 8.5s 실측이 평균을 무의미하게 함)러너 측 perf_counter — 라이브 경로 무변경
embed_calls · expanded_nodes · propagated_nodes · pool_chunks · llm_calls(항상 0 = 계약)contextvar 카운터(기본 no-op) + expand()/search() 반환값

비교는 파레토 — 품질과 비용을 하나의 점수로 합치지 않는다 (가중치를 지어내는 것). "벡터만"이 품질은 낮아도 비용이 훨씬 싸면 프런티어에 남는다 — 그게 정답일 네임스페이스도 있다.

Tier축비용규율

5. 핵심 설계 결정 4가지

결정근거 (전부 이 저장소의 실측)
레코드에 그래프 상태 지문 필수 (nodes·edges·coverage·hash) max_terms 스윕이 그래프 상태에 따라 두 번 뒤집혔다. 지문이 다른 레코드 간 비교는 화면에서 흐리게 + 경고, 추천에서는 거부
골든셋 지문도 필수 (n·statuses·hash) 라벨도 코퍼스 세대에 묶인다 (OCR 재인제스트 실측) — "같은 자로 쟀는가"가 레코드에 남아야 한다
eval_history 와 분리 저장 eval_history → latest_quality → /retrieve 의 품질 블록. 실험 레코드가 섞이면 라이브 응답이 실험 설정의 품질을 운영 품질로 보고한다
표본 n<50 이면 추천 거부 (small_sample 경고) 47케이스 과적합 경고 — 1건=0.02 인 자로 knob 을 확정하지 않는다. 현재 골든셋: PROJ-A 65 (confirmed 0 — statuses 명시 필수), ins 47
